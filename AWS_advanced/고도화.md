## 🟢 1. 쉽게 이해하는 전체 구조  

Docker 컨테이너는 AWS를 조작하는 도구 상자다. EC2는 AWS에 있는 별도의 서버다. 도구 상자를 지워도 AWS 서버는 남는다.  

```text
사용자 명령 또는 편의 Wrapper  
    ↓  
Docker Compose의 aws-lab 서비스  
    ↓  
Ubuntu 컨테이너의 Bash  
    ↓  
entrypoint.sh → 명령별 Script → 공통 함수  
    ↓  
AWS CLI → AWS 리소스  
```

| 용어 | 풀네임 또는 뜻 | 이 프로젝트에서 하는 일 |  
| --- | --- | --- |
| AWS | Amazon Web Services | 클라우드 리소스를 제공 |  
| CLI | Command Line Interface | 터미널 명령으로 도구 사용 |  
| Bash | Bourne Again SHell | 컨테이너의 표준 Shell |  
| OS | Operating System | Windows, macOS, Linux 같은 운영체제 |  
| Wrapper | 다른 명령을 감싸는 편의 프로그램 | 동일한 Compose 명령을 대신 호출 |  
| VPC | Virtual Private Cloud | 실습용 네트워크 |  
| IGW | Internet Gateway | VPC의 인터넷 연결 통로 |  
| EC2 | Elastic Compute Cloud | 웹 서버를 실행하는 가상 컴퓨터 |  
| EBS | Elastic Block Store | EC2가 사용하는 디스크 |  
| IAM | Identity and Access Management | AWS 권한 관리 |  
| SSH | Secure Shell | 서버 원격 접속 |  
| HTTP | Hypertext Transfer Protocol | 웹 응답 확인 |  

Docker, Compose, Nginx는 이 문서에서 임의로 약어 풀네임을 만들지 않는다.

## 🟢 2. 공식 Cross-platform 실행 계약  

### 🟡 공통 실행 조건  

- Windows는 Linux 컨테이너 실행 환경을 사용한다.  
- 각 OS에 Docker와 Compose v2가 준비되어 있어야 한다.  
- 공식 명령은 `AWS_advanced/` 디렉터리에서 실행한다.  
- 공식 명령을 쓰기 위해 호스트에 Bash, Make, AWS CLI를 추가로 설치할 필요가 없도록 만든다.  
- 호스트 CPU가 ARM64인 Apple Silicon과 AMD64인 일반 PC 모두에서 사용할 이미지와 설치 파일을 선택한다. 실제 지원 여부는 구현 후 따로 검증한다.  

```bash
docker compose run --rm aws-lab up # 실습 AWS 리소스 생성과 웹 서버 준비를 요청한다.  
docker compose run --rm aws-lab status # 실습 리소스 상태를 조회한다.  
docker compose run --rm aws-lab health # 웹 응답의 HTTP 상태와 본문을 확인한다.  
docker compose run --rm aws-lab ssh # 컨테이너의 SSH 도구로 EC2에 접속한다.  
docker compose run --rm aws-lab down # 삭제 대상을 확인한 후 실습 AWS 리소스를 정리한다.  
```

| 명령 요소 | 뜻과 설명 |  
| --- | --- |
| `docker` | Docker CLI를 실행 |  
| `compose` | Compose 설정의 서비스를 사용 |  
| `run` | 서비스 설정으로 일회성 컨테이너 실행 |  
| `--rm` | remove의 약자이며, 실행 종료 후 해당 컨테이너 자동 삭제 |  
| `aws-lab` | Compose 서비스 이름 |  
| `up` | 실습 생성 명령. Compose 자체의 `up`과 구분 |  
| `status` | 상태 조회 |  
| `health` | 서비스 정상 응답 확인 |  
| `ssh` | Secure Shell 접속 |  
| `down` | 실습 삭제 명령. Compose 자체의 `down`과 구분 |  

`--rm`은 AWS 리소스, 이미지, 연결한 영구 저장소를 정리하는 명령이 아니다. `docker compose down`도 이 프로젝트의 AWS 정리 명령을 대신하지 않는다. 일회성 컨테이너의 동작은 [Docker 공식 문서](https://docs.docker.com/reference/cli/docker/compose/run/)를 기준으로 한다.  

### 🟡 Bash 사용자용 편의 Wrapper  

```bash
./aws-lab up # 같은 Compose 서비스에 up을 전달한다.  
./aws-lab status # 같은 Compose 서비스에 status를 전달한다.  
./aws-lab health # 같은 Compose 서비스에 health를 전달한다.  
./aws-lab ssh # 같은 Compose 서비스에 ssh를 전달한다.  
./aws-lab down # 같은 Compose 서비스에 down을 전달한다.  
```

`./`는 현재 디렉터리에 있는 파일이라는 뜻이다. Bash Wrapper는 실행 권한을 보장한다.  

### 🟡 Windows PowerShell 사용자용 편의 Wrapper  

```powershell
.\aws-lab.ps1 up # 같은 Compose 서비스에 up을 전달한다.  
.\aws-lab.ps1 status # 같은 Compose 서비스에 status를 전달한다.  
.\aws-lab.ps1 health # 같은 Compose 서비스에 health를 전달한다.  
.\aws-lab.ps1 ssh # 같은 Compose 서비스에 ssh를 전달한다.  
.\aws-lab.ps1 down # 같은 Compose 서비스에 down을 전달한다.  
```

`.\`는 현재 디렉터리의 파일을 뜻한다. PowerShell Wrapper도 구현 대상으로 포함한다. 실행 정책으로 차단되면 공식 Docker 명령을 사용하며, 시스템 전체 실행 정책 변경을 요구하지 않는다. CMD에서는 공식 Docker 명령을 사용한다.  

### 🟡 모든 진입점이 지킬 규칙  

- 두 Wrapper는 같은 `compose.yaml`의 `aws-lab` 서비스만 호출한다.  
- AWS 생성·조회·삭제 로직은 Wrapper에 넣지 않는다.  
- 인자를 순서와 경계를 보존하여 전달한다. 공백이 있는 경로도 처리한다.  
- Wrapper는 자신의 위치를 기준으로 Compose 파일과 실행 디렉터리를 결정한다.  
- Docker의 종료 코드를 그대로 반환한다. 실패했는데 성공 코드로 끝내지 않는다.  
- SSH와 삭제 확인에 필요한 표준 입력을 전달한다.  
- 컨테이너의 entrypoint가 `up`, `status`, `health`, `ssh`, `down`을 분기한다. 명령 이름을 Ubuntu 실행 파일처럼 직접 실행하지 않는다.  
- 알 수 없는 명령은 사용법과 오류를 표시하고 실패 코드로 종료한다.  
- 명령을 생략하거나 `help`를 입력하면 사용법만 표시하고 성공 코드로 종료한다. `help`는 AWS 인증 확인이나 API 호출을 하지 않는다.  
- 지원 옵션을 문서에 명시하고, 알 수 없는 옵션은 오류로 처리한다. Wrapper는 임의의 Docker 옵션을 추가하거나 삭제하지 않는다.

구현할 때 Docker 이미지 빌드 Context는 `AWS_advanced/`로 제한한다. 실행 Script는 이미지에 포함하고, 변경 후 다시 빌드한다. 호스트의 Script를 덮어쓰는 개발용 Mount는 공식 실행 구성에 넣지 않는다. 컨테이너 내부 작업 경로는 `/app`으로 통일한다.  

단계별 Script는 학습 단위이고, `commands/`는 단계를 묶는 역할이다. 공통 함수는 `lib/` 한 곳에 둔다. 모든 코드에는 줄마다 쉬운 설명 주석을 넣는다.

## 🟢 4. 설정·인증·영구 저장  

- 설정 파일 이름은 `config/aws-basic-lab.env`로 정한다. 일반 규칙은 `프로젝트명.env`다. 환경 구분이 추가로 필요하면 별도 이름 규칙을 문서에 확정한다.  
- Compose가 설정을 컨테이너 환경변수로 전달한다. `.env`를 임의의 Bash 코드처럼 `source`하지 않는다.  
- 환경파일에는 Project, 실습 식별값, 리전, 프로필, 네트워크 범위, SSH 허용 IP 같은 설정을 둔다.  
- AWS Access Key, Secret Key, Session Token은 이미지·설정 예시·로그에 넣지 않는다. 필요한 AWS 인증 파일만 읽기 전용으로 연결하는 방식을 설계한다.  
- 계정 ID, 리전, Project, 실습 식별값이 예상 대상과 일치하는지 먼저 확인한다. 누락된 설정을 임의의 계정이나 리전으로 대체하지 않는다.  
- `runtime/`을 영구 저장 경로로 연결한다. 컨테이너 종료 후에도 상태정보와 개인키가 남도록 한다.  
- `.gitignore`의 현재 `.env` 규칙만으로 `aws-basic-lab.env`까지 제외된다고 가정하지 않는다. 해당 설정 파일과 `runtime/`을 명시적으로 제외한다.  
- `.dockerignore`에서도 설정 원본, 개인키, 인증정보, 상태정보, 로그를 제외한다.  
- Windows 호스트의 파일 권한 차이를 고려해 개인키를 컨테이너 내부 임시 경로에 복사하고 제한된 권한으로 사용한다. 원본은 출력하지 않는다.  
- SSH 호스트 키 검증을 유지한다. 검증을 무조건 끄는 옵션을 기본값으로 사용하지 않는다.

### 🟡 설정값의 이름과 검증 기준  

아래 변수명을 코드·설정 예시·사용 설명서에서 동일하게 사용한다. 실제 계정 정보나 인증값을 문서 예시에 넣지 않는다.  

| 변수 | 용도 | 검증 기준 |  
| --- | --- | --- |
| `PROJECT` | 프로젝트 Tag | 비어 있으면 중단 |  
| `LAB_ID` | 같은 프로젝트 안에서 실습 구분 | 계정·리전·Project와 함께 리소스 소유 범위 결정 |  
| `EXPECTED_ACCOUNT_ID` | 사용할 AWS 계정 | 인증 결과와 일치해야 함, 로그에서는 마스킹 |  
| `AWS_REGION` | 리소스 생성 위치 | 과제 기준인 `ap-northeast-2`만 허용 |  
| `AWS_PROFILE` | 사용할 인증 프로필 | 실습 전용 인증 파일에 존재해야 함 |  
| `VPC_CIDR` | VPC 주소 범위 | 유효한 IPv4 CIDR이어야 함 |  
| `SUBNET_CIDR` | Public Subnet 주소 범위 | VPC 범위 안에 있어야 함 |  
| `SSH_ALLOWED_CIDR` | SSH 접속 허용 범위 | 기본은 학습자 IPv4 주소의 `/32`, 전체 공개 금지 |  
| `INSTANCE_TYPE` | EC2 크기 | 선택한 AMI의 CPU 아키텍처와 호환 |  
| `AMI_ID` | 서버 운영체제 이미지 | 해당 리전의 Ubuntu LTS 이미지, SSH 사용자는 `ubuntu` |  

설정 검사는 명령에 필요한 범위로 나눈다. `help`는 AWS 설정을 검사하지 않고, `status`와 `down`은 계정·리전·소유 범위·인증만 필수로 요구한다. `up`은 네트워크·AMI·인스턴스 설정까지 검사한다. `ssh`와 `health`는 조회한 EC2와 개인키를 확인한다. 이미 생성한 리소스를 정리할 때 AMI 설정 누락 때문에 `down`이 막히지 않도록 한다.  

CIDR은 Classless Inter-Domain Routing, AMI는 Amazon Machine Image, LTS는 Long Term Support다. 로컬 Docker 이미지의 CPU 아키텍처와 AWS EC2의 CPU 아키텍처는 별개다. 기존 문서의 Ubuntu SSH 사용자와 설치 명령을 유지하려면 Amazon Linux AMI를 혼용하지 않는다.  

### 🟡 Compose 설정과 컨테이너 설정 구분  

- `env_file: ./config/aws-basic-lab.env`는 컨테이너에 전달할 설정이다. 이것만으로 Compose 파일 안의 `${변수}`나 호스트 Mount 경로가 채워지는 것은 아니다.  
- 공식 구성의 호스트 경로는 `./config/aws`, `./runtime`처럼 Compose 파일 기준 상대경로로 고정한다. 컨테이너는 인증 파일을 `/run/aws`에 읽기 전용으로 연결한다.  
- Compose에는 `AWS_CONFIG_FILE=/run/aws/config`, `AWS_SHARED_CREDENTIALS_FILE=/run/aws/credentials`를 지정한다. 파일명과 경로를 호스트 OS에 따라 바꾸지 않는다.  
- 핵심 실습 설정은 `env_file`에서 읽고, Compose `environment`에서 같은 변수를 중복 정의하거나 호스트 값을 자동 전달하지 않는다.  
- 표준 실행에서는 `-e`로 계정·리전 설정을 덮어쓰지 않는다. 컨테이너 안에서도 인증 대상과 설정을 확인한다.  
- `.env`의 자동 로딩이나 호스트 Shell의 인증변수에 의존하지 않는다. 다른 Compose 파일을 지정하는 `COMPOSE_FILE` 같은 호스트 설정은 공식 실행 전 해제하도록 안내한다.  

설정 적용 순서는 [Docker 환경변수 우선순위](https://docs.docker.com/compose/how-tos/environment-variables/envvars-precedence/), 경로 등의 변수 치환은 [Docker 변수 치환 문서](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/)를 기준으로 한다.  

### 🟡 인증 방식과 로그 범위  

- 첫 구현은 실습 전용 `config/aws/config`와 `config/aws/credentials`의 파일 기반 프로필을 지원한다. 호스트 전체 인증 폴더를 연결하지 않는다.  
- 임시 인증정보를 사용하면 Session Token과 유효기간도 확인한다. 만료되면 오류를 표시하고 중단한다.  
- SSO 등 로그인 과정에서 캐시 쓰기가 필요한 방식은 첫 구현의 지원 범위에서 제외한다. 지원할 때 별도의 로그인·캐시 정책과 검증을 추가한다. SSO는 Single Sign-On이다.  
- 파일 경로 환경변수의 동작은 [AWS CLI 설정·인증 파일 문서](https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-files.html)를 기준으로 한다.  
- `set -x`, 인증파일 출력, 전체 환경변수 출력, AWS CLI `--debug`를 기본 로그에 사용하지 않는다.  
- 계정 ID와 사용자 식별정보는 마스킹한다. 외부 공유 로그·스크린샷의 IP와 Resource ID는 검토 후 가린다. 개인키와 Token은 저장 로그에도 남기지 않는다.  
- Docker Socket이나 privileged 모드를 연결할 필요가 없는 실행 구조로 만든다.  
- IAM은 현재 과제의 최소권한 원칙을 유지한다. 생성뿐 아니라 조회·Tag·연결 해제·삭제에 필요한 권한을 목록화하고, 관리자 권한으로 오류를 우회하지 않는다.  
- 첫 구현은 구성된 파일 기반 프로필로 직접 EC2/VPC API를 호출한다. 별도 Role 전환이나 로그인 갱신을 요구하는 프로필은 지원 검증 후 추가한다.

## 🟢 5. `.gitattributes`와 Line Ending  

LF는 Line Feed, CRLF는 Carriage Return + Line Feed다. Windows에서 받은 Bash 파일이 CRLF이면 Ubuntu에서 실행 오류가 생길 수 있으므로 저장소 루트에 다음 정책을 적용할 계획이다.  

```gitattributes
# Bash Script는 Ubuntu에서 읽을 수 있도록 LF로 받는다.  
*.sh text eol=lf  
# 확장자가 없는 Bash Wrapper에도 LF를 적용한다.  
aws-lab text eol=lf  
# Docker 이미지 제작 파일은 LF로 통일한다.  
Dockerfile text eol=lf  
# 환경설정 파일은 LF로 통일한다. 비밀파일의 Git 제외는 별도로 처리한다.  
*.env text eol=lf  
# 환경설정 예시도 LF로 통일한다.  
*.env.example text eol=lf  
# Compose 설정 파일도 LF로 통일한다.  
*.yaml text eol=lf  
# PowerShell Wrapper는 Windows 사용을 고려해 CRLF로 받는다.  
*.ps1 text eol=crlf  
```

`text`는 텍스트 파일 처리, `eol`은 End Of Line 정책이다. [Git 공식 문서](https://git-scm.com/docs/gitattributes)의 정책을 기준으로 하며, 기존 추적 파일의 정규화는 대상 파일만 검토한 뒤 수행한다. Git에서 제외된 로컬 환경파일은 이 규칙만으로 변환되지 않으므로 생성·편집 시에도 LF를 지킨다.

## 🟢 6. 공통 출력 계약  

### 🟡 필수 함수  

| 함수 | 책임 | 출력 예시 |  
| --- | --- | --- |
| `info` | 일반 안내 | `ℹ️ [INFO] 리전 설정 확인` |  
| `success` | 성공 안내 | `✅ [SUCCESS] 인증 확인 완료` |  
| `warn` | 주의 안내 | `⚠️ [WARNING] 삭제 대상 확인 필요` |  
| `error` | 실패 안내 | `❌ [ERROR] 필수 설정 누락` |  
| `step_start` | 논리적 단계 시작 | `▶ [STEP] VPC 생성 시작` |  
| `step_end` | 단계 성공·실패 표시와 간격 출력 | `✅ [SUCCESS] VPC 생성 완료` |  

`step_start`는 단계 제목을 받고, `step_end`는 같은 제목과 실제 종료 코드를 받는다. `step_end`가 성공 여부를 임의로 판단하지 않는다. 단계마다 시작·종료 메시지는 한 번씩만 표시한다. 개별 Script와 명령 조합 Script가 같은 단계를 이중으로 감싸지 않는다.  

```text
▶ [STEP] VPC 생성 시작  

... 민감정보를 제외한 AWS CLI 결과 ...  

✅ [SUCCESS] VPC 생성 완료  



▶ [STEP] Public Subnet 생성 시작  
```

### 🟡 줄바꿈과 실패 처리  

- 논리적 Command 또는 Step이 끝나면 종료 메시지의 줄 끝에 더해 `printf '\n\n\n'`을 실행한 것과 같은 간격을 추가한다.  
- 이 처리는 `step_end` 한 곳에 둔다. 각 Script에 같은 줄바꿈 코드를 반복하지 않는다.  
- 내부 보조 명령마다 빈 줄을 넣지 않는다. 사용자에게 보여주는 단계 경계에 적용한다.  
- 실패한 단계도 오류와 간격을 출력하고 원래 실패 코드를 유지한다.  
- `set -e` 때문에 오류 처리에 도달하기 전에 종료되는 문제를 고려해, 단계 실행 결과를 명시적으로 검사한다.  
- zsh의 `precmd` Hook을 사용하지 않는다. 표준 Shell은 Docker Ubuntu의 Bash다.  

### 🟡 데이터와 안내 메시지 분리  

- Resource ID를 반환하는 함수의 stdout에는 값만 넣는다.  
- 안내와 오류는 stderr로 출력한다. ID를 변수에 저장할 때 안내 문구나 색상 코드가 섞이지 않게 한다.  
- 사용자용 상태 표는 stdout으로 출력할 수 있다. 데이터 반환 함수와 역할을 구분한다.  
- 종료 코드 0은 성공, 0 이외는 실패다. 인증 실패나 권한 부족을 리소스 없음으로 표시하지 않는다.  
- AWS CLI의 Pager를 비활성화해 일회성 명령이 화면 대기로 멈추지 않도록 한다.  

### 🟡 색상 정책  

| Label | 색상 |  
| --- | --- |
| INFO / STEP | 파랑 계열 |  
| SUCCESS | 초록 계열 |  
| WARNING | 노랑 계열 |  
| ERROR | 빨강 계열 |  

TTY는 Teletypewriter에서 유래한 터미널 개념이고, ANSI는 American National Standards Institute다. 출력할 스트림이 TTY일 때만 ANSI 색상을 사용한다. 로그 파일에는 색상 제어 문자를 남기지 않는다. `NO_COLOR` 설정도 존중한다. 색상이 없어도 아이콘과 Text Label로 의미를 알 수 있게 한다.

## 🟢 7. 명령별 AWS 동작과 안전 기준  

| 명령 | 동작 | 완료 기준 |  
| --- | --- | --- |
| `up` | 환경 확인 → 네트워크 → 보안그룹·키 → EC2 → Nginx → 검증 | 필요한 리소스 준비와 health 검증 통과 |  
| `status` | 현재 AWS 상태 조회 | 리소스별 현재 상태 또는 조회 실패 원인 표시 |  
| `health` | SSH로 내부 웹 응답 확인 후 컨테이너에서 외부 `/health` 확인 | 내부·외부 모두 HTTP 200과 정해진 본문 `OK` 확인 |  
| `ssh` | 대상 EC2와 개인키 확인 후 접속 | SSH 종료 코드 전달 |  
| `down` | 대상 목록 확인과 삭제 동의 → 의존관계 순서로 정리 | 관리 대상의 삭제·종료 상태 재조회 |  

- SSH 22번은 학습자 IP 또는 지정 대역으로 제한하고, HTTP 80번은 과제 기준에 맞게 허용한다.  
- 조회된 리소스가 여러 개면 첫 번째 결과를 선택하지 않는다. 대상 충돌을 표시하고 중단한다.  
- 재실행은 동일 실습의 기존 리소스를 조회하고 설정 일치를 확인한다. 실패했다고 무조건 새 리소스를 추가하지 않는다.  
- 가능한 리소스는 생성 요청에 Tag를 포함하고, 응답의 식별정보를 즉시 저장한다. 별도 Tag 작업이 필요한 리소스는 생성 직후 처리한다. 부분 실패 시 완료 단계와 남은 정리 대상을 알려준다.  
- `status`는 확인하지 않은 Nginx 상태나 HTTP 응답을 정상이라고 추측하지 않는다.  
- 대기와 재시도에는 시간·횟수 제한을 둔다. 영구 대기를 방지한다.  
- `down`은 계정·리전·Project·실습 식별값과 실제 삭제 대상을 보여주고 `DELETE` 입력을 요구한다. 비대화형 실행은 명시적 동의가 없으면 실패한다.  
- 첫 구현의 `down`은 대화형 확인만 지원한다. 자동 승인 옵션은 구현하지 않으며, 비대화형 삭제는 실패한다. 이후 자동화를 추가할 때 대상 고정과 동의 전달 규칙을 별도로 정의한다.  
- 삭제는 EC2 종료와 완료 대기 → 관리 대상 잔여 EBS·Elastic IP 및 키페어 확인·정리 → Security Group → Route Table 연결 해제와 삭제 → IGW 연결 해제와 삭제 → Subnet → VPC 순서를 기본으로 한다.  
- 기본 Route Table이나 다른 실습의 리소스는 삭제하지 않는다. 의존성 오류가 나면 원인을 표시하고 중단하며, 무관한 리소스를 강제 삭제하지 않는다.  
- 마지막에 관리 대상 잔여 리소스를 다시 조회한다. 확인 실패를 삭제 완료로 기록하지 않는다.  
- 인스턴스 유형만 보고 무료라고 단정하지 않는다. 실제 실행 전 계정의 혜택과 비용 조건을 별도로 확인한다.  


<br>

### 🟡 재실행·동시 실행·상태 복구  

- 상태정보는 계정·리전·Project·LAB_ID 단위로 분리하고, 형식 버전을 함께 저장한다. 상태파일을 Shell 코드처럼 실행하지 않는다.  
- 로컬 상태는 조회를 돕는 기록이다. 현재 AWS 상태를 확인하지 않고 로컬 ID만 믿어 수정하거나 삭제하지 않는다.  
- 로컬 기록이 없으면 Tag로 찾는다. EC2처럼 여러 개의 과거 종료 기록이 있을 수 있는 리소스는 현재 사용 가능한 대상과 종료 이력을 구분한다.  
- 기존 리소스 설정이 다르면 자동 교체하거나 새 리소스를 만들지 않고 차이를 표시한다.  
- 상태 저장은 임시 파일을 완성한 뒤 교체해 중간에 쓰다 만 파일을 줄인다.  
- 같은 실습의 `up`과 `down`은 공유 상태 경로에서 잠금을 획득한 실행 하나만 허용한다. 서로 다른 호스트의 로컬 잠금은 연동되지 않으므로 같은 실습을 여러 컴퓨터에서 동시에 변경하지 않는다.  
- 실행 중 종료되면 잠금 소유 정보와 실제 실행 상태를 확인한다. 오래됐다는 이유만으로 잠금을 자동 삭제하지 않는다.  
- 생성 요청이 Timeout으로 끝났다면 생성 실패로 단정하지 않는다. Tag와 요청 식별정보로 먼저 조회하고, 결과가 불명확하면 중단한다.  
- EC2 생성은 동일 요청에 동일 Client Token을 사용한다. 다른 생성 API에 같은 기능이 있다고 가정하지 않는다. 기준은 [AWS EC2 run-instances 문서](https://docs.aws.amazon.com/cli/latest/reference/ec2/run-instances.html)다.  
- 단계 실패 시 자동으로 전체 리소스를 삭제하지 않는다. 완료한 단계, 실패 원인, 다음 조회·정리 방법을 안내한다.  

### 🟡 개인키·웹 응답·삭제의 완료 기준  

- 개인키가 없는 기존 AWS Key Pair는 같은 이름으로 재생성하거나 정상 사용 가능하다고 처리하지 않는다. 오류와 복구 선택지를 안내한다.  
- 개인키를 처음 발급할 때 즉시 안전하게 저장하고, 실패하면 이후 EC2 생성을 중단한다. 키를 로그에 출력하지 않는다.  
- SSH 호스트 키는 최초 연결 시 Fingerprint를 확인하고 저장한다. 이후 변경되면 접속을 중단한다. 자동 설치 때문에 호스트 키 확인을 생략하지 않는다.  
- `up`의 Nginx 설치는 SSH를 이용하며, 서버 자체의 `/health`와 외부 `/health`가 모두 통과해야 완료한다. 완전 비대화형 생성은 초기 호스트 키 신뢰 절차를 별도로 설계·검증한 뒤 지원한다.  
- 내부 health는 EC2의 localhost에서 실행하고, 외부 health는 로컬 Ubuntu 컨테이너에서 EC2의 Public IP로 실행한다. 같은 Public IP에 두 번 요청한 것을 내부·외부 검사라고 부르지 않는다.  
- HTTP 상태와 본문을 분리해서 검사한다. 본문은 문서에 정한 끝 줄바꿈만 제거한 뒤 `OK`와 비교하고, 다른 본문이나 Redirect는 실패로 처리한다.  
- `health`는 연결 제한시간과 전체 요청 제한시간을 모두 둔다. SSH 단계 실패도 명령 실패로 처리한다.  
- 외부 검사는 현재 사용자 네트워크에서 접근 가능함을 증명한다. 모든 지역·모든 사용자에게 접속 가능하다는 증거로 확대하지 않는다.  
- `status`는 AWS 상태 조회만 수행한다. Nginx와 HTTP는 `health`에서 검사한다고 표시하고, 조회 성공과 웹 서비스 정상 여부를 구분한다.  
- 조회가 성공했지만 실습 리소스가 없으면 `status`는 `미생성`을 표시하고 성공 코드로 끝낸다. 필요한 리소스가 없는 `ssh`와 `health`는 실패한다. 상태 조회 중 일부 API가 실패하면 확인된 값과 오류를 함께 표시하고 실패 코드로 끝낸다.  
- `down`은 이미 삭제된 리소스는 건너뛰고, 조회·권한 실패는 오류로 처리한다. EC2는 종료 완료 상태를 확인하며 조회 목록에서 즉시 사라질 것을 요구하지 않는다.  
- 첫 구현에서는 Elastic IP와 NAT Gateway를 생성하지 않는다. 발견되더라도 소유 범위가 확인된 실습 리소스만 정리한다.  
- AWS 삭제 완료 후에도 로컬 개인키·known_hosts·기록은 자동 삭제하지 않는다. 별도 보관·삭제 방법을 사용 설명서에 적는다.  
- AWS 리소스 정리 확인과 Billing 반영 시점은 구분한다. 삭제 직후 비용이 0원이라고 단정하지 않는다.

## 🟢 8. 최초 준비와 구현 순서  

### 🟡 최종 사용자의 최초 준비  

| 순서 | 준비 | 완료 기준 |  
| --- | --- | --- |
| 1 | Docker 실행과 Compose v2 확인 | Linux 컨테이너 실행 가능 |  
| 2 | 예시를 복사해 `config/aws-basic-lab.env` 작성 | 필수 설정 검증 통과 |  
| 3 | 실습 전용 인증파일과 runtime 폴더 준비 | 파일 존재·연결 경로 확인, 인증파일은 Git 제외 |  
| 4 | Docker 이미지 빌드 | ARM64 또는 AMD64에 맞는 도구 준비 |  
| 5 | 도움말 확인 | AWS 요청 없이 명령 사용법 확인 |  
| 6 | `status`로 인증 대상과 현재 상태 확인 | 계정·리전 일치, 조회 성공 |  
| 7 | 사용자가 `up` 실행 | 최초 SSH 호스트 키 확인과 생성·health 성공 |  

```bash
docker compose build aws-lab # build는 Dockerfile로 실행 이미지를 만드는 명령이다. AWS 리소스를 만들지 않는다.  
docker compose run --rm aws-lab help # help는 준비된 이미지에서 사용법을 보여준다. AWS API를 호출하지 않는다.  
```

`help`는 유효한 AWS 인증정보를 요구하지 않는다. Compose의 env_file은 선택 항목으로 지정해 환경파일 없이 help를 실행할 수 있다. 다만 인증 폴더와 runtime Mount 경로는 사전에 준비되어 있어야 한다. AWS 명령은 설정 누락 시 실패한다. Docker가 이미지를 내려받거나 빌드하는 네트워크 동작은 AWS API 호출과 구분한다.  

### 🟡 학습·구현 순서  

- 기존 수동 실습과 과제 요구사항 확인 → 이미지 직접 다운로드와 컨테이너 수동 실행 → Bash와 AWS CLI 학습 → 공통 함수와 단계별 Script → 조회·health·정리 → 마지막에 Dockerfile·Compose·Wrapper 작성 순서로 진행한다.  
- `_practice/`는 목표 구조의 20~30번 문서로 나누고, 명령과 옵션의 뜻·실제 실행 위치·기대 결과·실패 시 확인 방법을 적는다.  
- Ubuntu 기반 이미지, AWS CLI, Compose 기능의 최소 지원 버전은 구현 시 실제 검증한 버전으로 고정하고 README에 기록한다. `latest`만으로 실행 환경을 정의하지 않는다.  
- 다운로드 설치 파일은 공급자의 검증 방법으로 확인한다. 새 도구나 AWS 권한을 추가하면 이유와 검증 결과를 기록한다.  
- 최종 설명서는 공식 명령을 먼저 안내하고 Wrapper를 다음에 소개한다. OS별 인증 준비 방법과 제출 문서 경로도 포함한다.

## 🟢 9. 구현 후 검증 기준  

| 검증 항목 | 방법 | 확인할 것 |  
| --- | --- | --- |
| Bash 기본 검사 | 문법 검사와 필요한 정적 검사 | 잘못된 문법·변수·인자 처리 |  
| Wrapper 일치 | Docker 호출을 모의 도구로 대체 | 동일 서비스, 인자 전달, 종료 코드 |  
| 출력 함수 | 성공·실패·비TTY 출력 비교 | 함수 6개, 단계 간격, ANSI 코드 제거 |  
| 값 반환 | 모의 Resource ID 조회 | stdout에 안내 문구가 섞이지 않음 |  
| 설정과 보안 | 비밀값 없는 가짜 설정으로 검사 | 누락 시 중단, Git·빌드 제외 규칙 |  
| 재실행과 실패 | 리소스 없음·중복·부분 완료·권한 실패 모의 응답 | 중복 생성과 잘못된 대상 삭제 방지 |  
| 동시 실행과 복구 | 같은 실습 명령 중복 실행과 중간 종료 모의 검사 | 잠금, 불완전 상태파일, 결과 불명확 시 생성 중단 |  
| 명령별 설정 | 생성 설정 일부가 빠진 가짜 환경 | help·status·down에 불필요한 생성 설정을 강제하지 않음 |  
| SSH와 health | 가짜 SSH·HTTP 응답과 호스트 키 변경 | 개인키 누락, HTTP 오류·Redirect·잘못된 본문 탐지 |  
| 정리 재실행 | 이미 삭제된 리소스와 종료 이력 모의 응답 | 정리 완료와 조회 실패 구분, 로컬 개인키 보존 |  
| 줄바꿈 | Git 속성과 실제 파일 바이트 확인 | Bash LF, PowerShell 정책 적용 |  
| 이미지 | ARM64·AMD64에서 준비와 도움말 실행 | 지원 아키텍처와 도구 실행 |  
| OS 호환 | macOS·Linux·Windows에서 공식 명령 검증 | 경로, 입력, 파일 권한, 종료 코드 |  
| 실제 AWS | 사용자가 별도로 지시한 경우에만 수행 | 생성·조회·접속·health·정리의 실제 결과 |  

모의 응답과 로컬 검사 통과는 실제 AWS 동작 성공을 증명하지 않는다. Windows 또는 Linux에서 실행하지 않았다면 미검증으로 표시한다. 구현 후 변경 내용을 한 번 더 검토하고, 검증한 범위만 완료로 기록한다.  

현재 문서는 설계 단계다. 이 표의 검증이 실행되었다는 뜻이 아니다. 공개 README에는 실제 실행한 OS·CPU·도구 버전과 결과만 기록한다.

## 🟢 10. 구현 경로와 확인할 문서

구현은 현재 프로젝트 이름인 `AWS_advanced/`를 사용한다. 실행 방법과 지원 범위는 `README_Docker_Enhanced.md`, 모의 검증은 `tests/run_tests.py`, 학습 순서는 `_practice/`의 AWS 고도화 문서를 참고한다. 최초 생성은 대화형 up만 지원하고, 자동 승인 삭제는 지원하지 않는다.

호스트 파일 권한용 `LAB_UID`·`LAB_GID`만 Compose 변수 치환을 사용한다. 핵심 AWS 설정은 `env_file`만 사용한다. 최종 IAM 호출 목록은 `docs/iam-actions.md`, 검증 근거는 `tests/VALIDATION.md`에 둔다.
